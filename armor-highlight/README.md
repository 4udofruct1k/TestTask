# Подсветка брони (max.armor-highlight)

Мод для «Мира танков» 1.45.0.0. Постановка задачи: [ARMOR_SPEC.md](ARMOR_SPEC.md).

В бою мод раскрашивает вражеский танк под прицелом по вероятности пробития текущим снарядом:

- **100%** — зелёный;
- меньше 100% — постепенный переход к оранжевому, **50%** — оранжевый;
- дальше переход к красному;
- **не пробивает или нет урона** (рикошет, экран, модуль без урона) — красный.

По умолчанию подсвечивается круг вокруг центра прицела (радиус 60 px) по логике 0.3.0: круг сразу закрашивается грубо и за доли секунды становится точным, затем непрерывно пересчитывается. Если ячеек слишком много для пересчёта вживую, основа крупнее ячейки, а до ячейки из настроек уточняются только границы цветов и край силуэта — однородная броня остаётся крупными блоками. Для проверки можно подсветить всю цель. Настройки и режим просмотра открываются в ангаре.

**Статус.** В игре проверены 0.2.0 (квадраты белые), 0.3.0 (цвета из текстур, ячейка 3 px — работала быстро и без лагов) и 0.4.0: в ангаре подсветка вышла больше танка и вся красная (причины и исправления — в «Истории»). 0.5.0–0.7.x подсвечивали всю цель или круг по 1 px и тормозили (см. «Историю»). По логу 0.7.1: точка в бою стоит ~22 мкс, в ангаре ~52 мкс. С 0.9.0 область у прицела снова считается по логике 0.3.0 — в игре «гораздо лучше». Своя текстовая панель настроек 0.11.0 в игре выглядела плохо; с 0.12.0 настройки снова в окне ModsSettingsAPI. Уточнение границ (0.10.0), прогрузка заранее и подпись у прицела (0.12.0) в игре ещё не проверялись.

## Сборка

Нужны Python 2.7 и 7-Zip.

```
build.bat -v 0.12.0
build.bat -v 0.12.0 -i "D:\Games\Tanki"
build.bat -v 0.12.0 -i "D:\Games\Tanki" -m 1.45.0.0
```

Первая команда только собирает `max.armor-highlight_0.12.0.mtmod` рядом с `build.bat`. С флагом `-i` скрипт копирует пакет в `<игра>\mods\<версия клиента>\`.

- Текстуры палитры (`res/gui/maps/armor_highlight/*.dds`, около 3600 файлов по 192 байта) и иконку для списка модов (`res/gui/maps/icons/armor_highlight/icon.png`) генерирует `tools/make_textures.py` при сборке, в репозитории их нет. Клиент монтирует папку `res` из `.mtmod` как корень ресурсов (`paths.xml`: `<Path mask="*.mtmod" root="res">`), поэтому файлы клиента не затрагиваются.
- Python ищется так: переменная `PYTHON27` (полный путь к `python.exe`), потом `py -2.7`, потом `python`. Версия проверяется, сборка на 3.x не пройдёт.
- Папку версии клиента внутри `<игра>\mods\` скрипт находит сам, если она одна. Иначе он выведет список, и папку нужно передать через `-m`.
- При установке скрипт удаляет из этой папки прошлые сборки `max.armor-highlight_*.mtmod`, чтобы клиент не загрузил две версии сразу. Перед установкой закрой игру.

## Настройки

Окно «Подсветка брони» в «Настройках модификаций» (ModsSettingsAPI): флажки, ползунки, списки, выбор цвета и клавиши. Если какого-то элемента в установленной версии ModsSettingsAPI нет, вместо него ставится список, а не пропадает всё окно; ошибки пишутся в `python.log` строками `ModsSettingsAPI template ...`.

- Значения применяются сразу и дублируются в `mods_armor_highlight/settings.json` рядом с `preferences.xml` клиента (там же клиент хранит свои кэши). Значения из окна главнее файла.
- **Запасная панель — Ctrl+Shift+Y в ангаре.** Работает всегда, на случай если окна мода в «Настройках модификаций» не видно. Без ModsSettingsAPI её открывает и пункт «Подсветка брони: настройки» в списке модов (ModsList API).
  - Стрелки вверх/вниз — пункт, влево/вправо — значение, Enter — переключить. «Клавиша вкл/выкл в бою»: Enter, затем нужная клавиша или сочетание (Backspace — отмена). Цвета выбираются из набора. Внизу — «Просмотр на танке» и «Сбросить все настройки» (два Enter подряд).
  - Стрелки при открытой панели получает и интерфейс ангара: мод не может перехватить нажатие.
- В логе при запуске: `ModsSettingsAPI: settings window registered, N + M controls` или `ModsSettingsAPI not found, ...`.

| Настройка | По умолчанию | Что делает |
|---|---|---|
| Включить или выключить в бою | Y | Клавиша или сочетание. В начале боя подсветка всегда включена |
| Показывать в движении | да | Если выключено, подсветка только когда свой танк стоит |
| Показывать в аркадном режиме | да | Если выключено, только снайперский режим |
| Не убирать, когда прицел уходит с цели | да | Подсветка остаётся на последней цели, пока прицел не на другом противнике |
| Где подсвечивать | вокруг центра прицела | «Вокруг центра прицела» — круг, в нём каждая ячейка. Для проверки — вся цель: с уточнением, каждая ячейка в фоне (бюджет 25 мс, картинка появляется целиком) или каждая ячейка за один кадр (игра замирает) |
| Размер области у прицела | радиус 60 px | 40, 60, 80, 120 или 160 px. Точек — как квадрат радиуса: вдвое больше радиус — вчетверо дольше прорисовка |
| Задержка появления | 100 мс | С момента, когда цель под прицелом |
| Размер ячейки | 3 px | 1, 2, 3, 4 или 8 px. Если ячеек в круге больше 2500, основа крупнее (шаг удваивается), а границы цветов и край силуэта уточняются до этого размера. Точка в бою стоит ~22 мкс; круг 60 px с ячейкой 3 px пересчитывается за ~0.2 с, с ячейкой 1 px и уточнением — за ~0.45 с (вместо ~1.4 с сплошь). Для всей цели размер округляется вниз до степени двойки (3 → 2 px), на огромной цели растёт сам: не больше 400 строк |
| Шаг поиска мелких зон | авто | Только для «Вся цель, с уточнением»: авто (8–16 px по размеру цели), 16, 8, 4 или 2 px. Зона меньше шага может потеряться вне круга под прицелом |
| Полная проверка под прицелом | радиус 20 px | Только для «Вся цель, с уточнением»: выкл, 10, 20 или 40 px. В круге считается каждая ячейка, он считается первым |
| Прогрузка танка заранее | 25% | Выкл, 10, 25 или 50%. Какая доля расчёта идёт на весь танк вне круга, от прицела наружу: сначала крупные блоки, потом мельче, до основы, затем по кругу пересчитываются. При переводе прицела на другое место танка там уже есть картинка. FPS не меняется (бюджет тот же), круг у прицела обновляется на эту долю медленнее |
| Подпись у прицела | да | Справа от центра прицела: шанс пробития в точке прицеливания и модули на пути снаряда. См. «Подпись у прицела» |
| Нагрузка на процессор в бою | 3 мс/кадр | Бюджет расчёта точек за кадр. Больше — быстрее прорисовка, ниже FPS |
| Нагрузка в режиме просмотра | 10 мс/кадр | То же в ангаре, где точка дороже (~52 мкс). От 5 до 50 мс |
| Пробитие 100%, 50%, не пробивает | зелёный, оранжевый, красный | Цвета градиента |
| Оттенков в переходе | 7 | 3, 5, 7 или 11 |
| Непрозрачность | 50% | От 10 до 100% с шагом 10 |
| Способ окраски | текстуры из пакета | См. «Цвет» |

## Подпись у прицела

В бою справа от центра прицела — шанс пробития в точке прицеливания, например `50% · модули: гусеница, двигатель`.

- Точка и направление — как у ванильного маркера орудия; шанс — тот же расчёт, что у подсветки.
- **Модули** — части танка на пути снаряда, до которых он может дойти при лучшем броске пробития (номинал + разброс), то есть которые выстрел в эту точку может задеть. Проход по слоям тот же, что в «Вероятности пробития», но не останавливается на первом листе с уроном: за пробитой бронёй снаряд идёт дальше, пока у него остаётся пробитие. Модуль — слой, у материала которого есть `extra` (`leftTrack0Health`, `engineHealth`, `gunner1Health` и т. п.).
- **Ограничение.** Видны только модули, которые есть в клиентской модели столкновений танка (`collisionModelClient`). Внутренние модули и экипаж, скорее всего, есть только в серверной модели (`collisionModelServer`), и тогда подпись покажет только внешние: гусеницы, орудие. Проверка — строка лога `aim layers (танк): ...` (в debug, один раз на цель): все слои под прицелом с материалом, бронёй и `extra`.
- Для фугасов с новой механикой (считаются по урону, см. «Вероятность пробития») подписи нет.
- В режиме просмотра модули пишутся в подсказке после шанса под курсором.

## Режим просмотра в ангаре

Пункт «Просмотр на танке» в запасной панели (Ctrl+Shift+Y) или кнопка модов в ангаре → «Подсветка брони: просмотр», если установлен ModsList API. Повторное включение выключает режим, выход из ангара — тоже.

- **Цель** — танк в ангаре: свой или открытый в предпросмотре из дерева исследований.
- **Стрелок** — танк, выбранный в карусели. Орудие и снаряд переключаются клавишами:
  - **1–4** — снаряд;
  - **G** — следующее орудие (все орудия всех башен);
  - **«-» и «=»** — дистанция, шаг 50 м, от 0 до 700.
- **Курсор мыши** — точка прицеливания: уточнение идёт от неё. В подсказке слева пишутся стрелок, орудие, снаряд с пробитием на выбранной дистанции и шанс пробития под курсором (сколько миллиметров надо пробить).
- Подсветка обновляется сама после «Применить» в настройках.

**Расчёт в ангаре упрощённый:** ванильного расчёта без боя нет.
- Слои брони — коллизия танка в ангаре (`appearance.collisions.collideAllWorld`), как в `Vehicle.collideSegmentExt`.
- Пробитие на дистанции — `_computePiercingPowerAtDistImpl` и `computeDistanceFactor`.
- Нормализация и рикошет — значения по умолчанию из клиента (`_ArenaModifiersVisitor`), формулы те же, что у `_shouldRicochet` и `_computePenetrationArmor`.
- Лучи идут от камеры ангара.

## Что проверить

**Ангар.** Режим просмотра: цвета должны лежать только на танке, без ореола вокруг. Шанс под курсором меняется при смене снаряда, орудия и дистанции. Круг у курсора должен заполняться примерно за секунду; раз в секунду в лог пишется строка `view mode stats ...` с ценой точки (`us per cell`) — пришли её.

**Бой.** Удобнее всего в тренировочной комнате с союзником в другой команде.

1. **Загрузка.** В `python.log` есть строки `[armor_highlight] init, version 0.12.0`, `settings: ...`, в бою `started in battle: ...`. Один раз пишется `screen: GUI.screenResolution=..., BigWorld.screenSize=...` — пришли её. При запуске игры пишется строка `bench: ...` — сколько на этом компьютере стоит пересечение луча с треугольником и с блоком на чистом Python и оценка луча по своей геометрии брони; сравни с `us per cell` в строках `stats` (цена точки через движок).
2. **Появление.** Подсветка включена с начала каждого боя, Y выключает и включает её. Через 0.1 с после наведения на врага круг у центра прицела сразу закрашивается грубо (ячейки по 24 px) и за несколько кадров становится точным — как в 0.3.0. Круг едет за прицелом; посчитанное запоминается, и при возврате прицела картинка появляется сразу.
3. **Градиент.** Цвета плавно меняются по броне. В центре каждой зоны цвет совпадает с ванильным маркером: зелёный маркер — зелёная или близкая к ней зона, красный — красная или оранжево-красная (см. «Вероятность пробития»).
4. **Движение камеры и цели.** Подсветка держится на броне ровной сеткой и едет вместе с целью без пересчёта. Круг непрерывно пересчитывается по очереди, каждая ячейка не чаще раза за кадр, поэтому поворот башни и смена угла обзора подхватываются за один круг пересчёта. При резком сдвиге (больше 16 px), смене снаряда или зуме круг строится заново.
5. **Условия.** Клавиша Y выключает и включает подсветку, в чате не срабатывает. Остальное — по настройкам выше.
   **Подпись у прицела.** Справа от прицела шанс пробития и модули. Наведи на гусеницу, на орудие, на корпус над двигателем. Пришли строки `aim layers (...)` из лога: по ним видно, есть ли в клиентской модели внутренние модули.
6. **Лог.** Пока подсветка активна, раз в секунду пишется строка (числа для примера):
   ```
   stats 1.0s: frames=360 active=358 computed/frame=136.1 (22 us per cell) compute avg=2.98 max=3.10 ms, render avg=0.40 max=2.10 ms, new grids=1 | cell=1px step=4 aim area r=60px cells=700 split=880 detail/cycle=2400 pending=0 cycles=12 quads=260/300 | vanilla check 259/259 ok
   ```
   - `compute` — расчёт точек (бюджет из настроек), `render` — сборка прямоугольников и перестановка квадратов. `us per cell` — сколько стоит одна точка: главное число для настройки, пришли его.
   - `new grids` — сколько раз круг или сетка строились заново.
   - `step` — шаг основы в ячейках, `cells` — блоков основы в круге, `split` — поделённых блоков (уточнение), `detail/cycle` — расчётов уточнения за круг пересчёта, `pending` — ещё не посчитанных блоков, `cycles` — полных кругов пересчёта, `quads` — показано/создано квадратов.
   - Для всей цели вместо этого: `search` — шаг поиска, `stage` — фаза (`uniform`, `sweep`, `refine` с длиной очереди, `full`, `done`), `cells` — посчитанных точек.
   - `vanilla check` — сколько выборочных сверок моего цикла по слоям с ванильным `getShotResult` совпало. Любое расхождение пишется в лог строкой `vanilla check: ...`, пришли её.
   Смены состояния пишутся строками `state: active` / `state: inactive, <причина>`, в режиме просмотра — `view mode: ...`.
7. **FPS.** Сравни с включённой и выключенной подсветкой. Нагрузку можно снизить настройками «Нагрузка на процессор в бою», «Размер области у прицела» и «Размер ячейки».
8. **Вся цель, каждая ячейка.** В логе строка `full pass (режим): N cells in T s of compute, X us per cell` — сколько ячеек, сколько времени расчёта и сколько стоит одна ячейка.
   - «За один кадр»: игра замирает на всё время расчёта. Весь Python игры и мода выполняется в одном основном потоке, коллизии движка вызываются только из него, поэтому другие ядра не помогают. Диспетчер задач при этом показывает среднюю загрузку по всем ядрам: одно ядро на 100% из 16–24 потоков — это всего 4–8%.
   - «В фоне»: FPS проседает, пока идёт расчёт, но игра не замирает. Старая картинка держится, пока новая не готова.
   - Здесь сетка пересобирается при сдвиге картинки цели больше чем на 3 px, а не на 1 px, иначе расчёт перезапускался бы от каждого доворота башни.

**Почему у WG подсветка не грузит процессор.** У WG это нативный модуль движка (`armor_flashlight`, CGF-компонент на C++): трассировку делает движок, раскраску модели — шейдер на видеокарте; Python только передаёт параметры. В клиенте Лесты такого модуля нет, поэтому здесь каждая точка — отдельный вызов коллизии из Python в основном потоке игры. Распределить это по ядрам нельзя: коллизии движка вызываются только из основного потока, в Python 2.7 потоки не выполняются параллельно, а отдельный процесс не видит моделей танков в памяти игры. Нагрузку ограничивают размер круга, кэш посчитанного и бюджет миллисекунд на кадр.

### Цвет

В 0.2.0 квадраты были белой текстурой с цветом через `colour`, и цвет не появился. `GUI` в этом клиенте — pybind11-обёртка над Scaleform (`GUI.Simple.colour` имеет тип `GUIComponentColour`, в логе `[Scaleform] Create GUI Component`), масштаб цвета у неё не описан. С 0.3.0 цвет и прозрачность запечены в текстуры.

Цвет из настроек приводится к ближайшему из палитры: куб 7×7×7 (шаг 42–43 на канал) плюс точные цвета градиентов по умолчанию, по 10 уровней непрозрачности. «Способ окраски» — запасные варианты, которые удобно сравнить в режиме просмотра:

- **Текстуры из пакета** — по умолчанию, проверено в 0.3.0.
- **Текстуры в памяти** — точный цвет. Мод собирает PNG и регистрирует его через `BigWorld.addScaleformTexture`, как клиент делает с эмблемами кланов, квадрат ссылается на `img://<id>`. Неизвестно, понимает ли `GUI.Simple` такие пути.
- **colour 0–255 и colour 0–1** — белая текстура и цвет через `colour` в двух масштабах. В 0.2.0 первый дал белые квадраты.

## Вероятность пробития

Ванильный индикатор (`_CrosshairShotResults`) отдаёт только три результата: пробьёт, может пробить, не пробьёт. Процент нужного пробития решающего листа (`piercingPercent`) он считает, но отдаёт только в отладочное событие. Поэтому `penetration.evaluate` повторяет цикл `__shotResultDefault` построчно. Всё остальное берётся из ванильного кода:

- коллизия — `collideDynamicAndStatic` и `_getAllCollisionDetails`;
- пробитие на дистанции — `_computePiercingPowerAtDist` и `computeDistanceFactor`;
- рикошет и приведённая броня — `_shouldRicochet` и `_computePenetrationArmor`.

Вероятность — доля случайного разброса пробития (`shell.piercingPowerRandomization`, обычно ±25%), при которой суммарная броня пробита. Распределение считается равномерным: 100% при `piercingPercent ≤ 75`, 50% при 100, 0% при 125 и выше.

Ванильный «может пробить» — это `piercingPercent` от 87.5 до 112.5. Поэтому ванильно-зелёные места между 75 и 87.5 выглядят желтовато-зелёными, а ванильно-красные между 112.5 и 125 — красно-оранжевыми. Это реальный шанс пробития.

Фугасы с новой механикой (`SHELL_MECHANICS_TYPE.MODERN`) считаются по урону, процента у них нет. Для них используется ванильный результат: 100%, 50% или 0%.

В debug-режиме каждый 50-й расчёт сверяется с ванильным `getShotResult`, итог — в строке `stats`.

## Как устроена отрисовка

- **Сетка привязана к цели.** Якорь — точка на цели в её системе координат. Каждый кадр он проецируется на экран и округляется до пикселя, ячейка `(i, j)` — пиксель со смещением `(i, j)` от якоря. Поэтому края ложатся на границы пикселей, а при повороте камеры вся картинка сдвигается без пересчёта.
- **Область у прицела** (`window.py`, по умолчанию) — логика 0.3.0 и уточнение границ.
  - Круг радиуса из настроек вокруг центра прицела: в бою — точка маркера орудия (даже если прицел ушёл с липкой цели), в режиме просмотра — курсор. Ячейка (i, j) — квадрат `cellPx` с углом `(i, j) * cellPx` от якоря на цели; значение блока — в центре его левой верхней ячейки.
  - Основа — блоки по 2^level ячеек: level растёт, пока в круге больше 2500 блоков. В режиме просмотра тогда пишется «Ячейка N px укрупнена до M px».
  - Сначала непосчитанные блоки от крупного уровня (шаг 8 блоков основы) к основе, в каждом — от центра; крупные уровни — с кольцом блоков вокруг. Пока блок не посчитан, рисуется значение ближайшего посчитанного крупного блока над ним, но только если все 8 соседей того крупного блока — на цели: иначе он лежит у края силуэта, и его цвет вылился бы за контур. Внутренность круга закрашена сразу, край силуэта — когда посчитан.
  - Заранее (настройка «Прогрузка танка заранее», по умолчанию 25%): в конце каждого круга пересчёта — такая доля блоков круга (не меньше 16) по габаритам цели, от прицела наружу. Сначала уровень под верхним, потом мельче, до основы; первый проход — только непосчитанное, дальше — пересчёт по кругу, чтобы не устаревало. Всё посчитанное лежит в кэше области. Когда прицел резко уходит на другое место танка, там сразу есть картинка (грубая или уже точная), и круг не обрывается.
  - Затем круг пересчёта, снова и снова (новый — не чаще раза за кадр): сначала уточнение, потом каждый блок основы и кольцо блоков вокруг круга — сначала блоки на границах (край силуэта, смена цвета), потом однородные. Уточнение: блок, у которого хоть один из 8 соседей того же уровня показывает другое (другой цвет или край силуэта), делится на 4, и так до ячейки из настроек; блоки основы — от центра. Однородная броня остаётся крупной; граница, которая пропала (цель повернулась), снова становится одним блоком. На синтетической цели с ячейкой 1 px это ~3.7 тыс. расчётов на круг 60 px вместо 11 тыс., картинка совпадает с точной до пикселя.
  - Растр: у каждой полосы блоков основы — интервалы по строкам ячеек (у поделённых блоков — по их листьям); куски по 16 строк склеиваются в прямоугольники и кэшируются, пока не меняются их полосы. Затем прямоугольники обрезаются по кругу: точно по горизонтали, полосками по 4 px по вертикали (`config.aimEdgePx`); целиком лежащие в круге не трогаются.
  - Новые значения попадают в картинку не чаще раза в 2 кадра и не дольше 1.5 мс сборки за раз (остальные полосы — в следующий раз); сдвиг круга за прицелом — сразу, квадраты едут за целью каждый кадр. Время сборки картинки вычитается из бюджета расчёта: «Нагрузка на процессор» — это всё время мода за кадр.
- **Вся цель, с уточнением** (`lattice.py`).
  - Область — габариты частей цели на экране (`model.getBoundsForPart`).
  - Сначала равномерная проверка: блоки 16–64 px по всей области, потом до блока `base` — шага поиска (авто: не больше 700 блоков).
  - Затем все блоки `base` проверяются на однородность: однородные сразу рисуются, и сплошная броня появляется на экране.
  - Остальные дробятся до размера ячейки в очереди по близости к прицелу, поэтому место под прицелом становится точным первым. Дробится блок, у которого хотя бы у одного из 8 соседей другое значение. Недостающие значения соседей досчитываются по требованию, так что порядок не влияет на точность.
  - В круге полной проверки вокруг прицела дробится всё, до каждой ячейки: там не теряются зоны меньше шага поиска. Когда прицел уходит, круг переезжает и заново открывает однородные блоки на новом месте.
  - Однородная броня остаётся крупными блоками, граница уточняется до пикселя. На синтетической цели 320×170 px это ~14 тыс. точек вместо 54 тыс., без ошибок на пикселях.
  - «Вся цель, каждая ячейка» считает каждую ячейку кольцами от прицела — в фоне или за один кадр.
  - Цена шага поиска: пятно 10×10 px посреди однородного листа при шаге 16 px теряется, при 4 px находится. Щель 6×20 px под прицелом с кругом 20 px становится точной через ~760 точек (при шаге 3 мс на кадр и ~50 мкс на точку — около 15 кадров); без круга она не находится.
  - Рисуются только окончательные блоки: ячейки нужного размера и однородные блоки, у которых проверены все соседи. Поэтому на экране нет грубых промежуточных блоков и подсветки вокруг силуэта. Тест сверяет это пиксель в пиксель на каждом шаге расчёта.
- **Отрисовка.** Блоки раскладываются по строкам, соседние интервалы одного цвета сливаются в полосы, одинаковые полосы соседних строк — в прямоугольники. Каждый прямоугольник — один `GUI.Simple`, позиция и размер в clip-координатах, сетка пикселей — `GUI.screenResolution()`. Неизменившийся прямоугольник сохраняет свой квадрат: при уточнении GUI трогается только там, где картинка поменялась.
- **Пересборка сетки всей цели.** Сетка строится заново, если картинка цели сдвинулась бы больше чем на 1 пиксель:
  - повернулись башня, орудие или корпус (сдвиг габаритов в системе координат цели);
  - камера смотрит под другим углом или с другой дистанции;
  - сменились зум, разрешение или снаряд.
  Недосчитанная сетка при сдвиге до 16 px сначала досчитывается, потом строится новая. Пока новая сетка без картинки, видна старая. Когда сетка готова, мод раз в кадр перепроверяет центр случайного однородного блока.

## История

- **0.2.0.** Квадраты белые: цвет через `colour` не применился. С 0.3.0 цвет в текстурах.
- **0.4.0.** В ангаре подсветка вышла больше танка и вся красная. Причин две:
  - Размер квадратов задавался в режиме PIXEL в единицах `BigWorld.screenSize()`, а у Scaleform-обёртки `GUI.Simple` эти пиксели другие (похоже, с учётом масштаба интерфейса). Каждый квадрат оказался больше своего места, и они перекрывали друг друга. С 0.5.0 размер задаётся в clip-координатах, как и позиция, а сетка считается в пикселях `GUI.screenResolution()`, как у клиента (`helpers/gui_utils.pixToClipVector2`).
  - Коллизия танка в ангаре содержит кроме частей танка увеличенные копии корпуса, башни и орудия для камеры (индексы частей 4–6, `hangar_vehicle_appearance.py`). Лучи упирались в них: брони у копий нет, по ванильной логике это «только крит», поэтому всё было красным. С 0.5.0 эти попадания отбрасываются, а слои сортируются по дистанции. В бою таких копий нет.

- **0.6.0.** Без полной проходки подсветка не появлялась: сетка всей цели начиналась заново от каждого сдвига картинки на 1 px, а на движущейся цели такой сдвиг бывает каждые несколько кадров, и сетка не доходила до первой картинки. Полная проходка «за один кадр» считала всю цель при каждом таком сдвиге, и игра замирала. С 0.7.0 по умолчанию — круг у центра прицела, пересчёт при сдвиге идёт поверх прежней картинки, а недосчитанная сетка всей цели досчитывается.

- **0.7.1.** В бою подтормаживало и замирало. Каждый прямоугольник — отдельный элемент интерфейса, который игра рисует, а мод переставляет в каждом кадре, когда сдвигается цель или камера. В 0.7.x прямоугольники резались по плиткам 8×8 px и выходило втрое больше, чем нужно (на круге 60 px — ~300 вместо ~100); в ранней 0.3.0 их было несколько десятков. Кроме того, с 0.6.0 недостающие квадраты создавались все в одном кадре, и игра замирала. С 0.7.2 интервалы сливаются через границы плиток, а квадратов создаётся не больше 32 за кадр, как в 0.3.0.

- **0.7.1, лог из боя.** Замирания на 1–4 с были в режиме «Вся цель, каждая ячейка за один кадр» с радиусом 160 px: каждый пересчёт считал весь танк (45–178 тыс. точек). Точка стоит ~22 мкс в бою и ~52 мкс в ангаре. Липкая цель хранилась как объект; когда танк ушёл из видимости, клиент уничтожил сущность, и обращение к ней (`isStarted`) давало ошибку в каждом тике до конца боя. С 0.8.0 липкая цель хранится по id и берётся из `BigWorld.entities`. Кроме того, в 0.7.x на экране оставались прежние значения, пока круг пересчитывался; с 0.8.0 устаревшие больше чем на 2 px сдвига убираются. Настройки сбрасываются (версия 7): ячейка по умолчанию 2 px.

- **0.7–0.8.** Круг у прицела заполнялся по 1–2 px от центра без грубой картинки и пересчитывался только при сдвиге цели, поэтому появлялся с задержкой. С 0.9.0 область снова считается по логике 0.3.0: сразу грубо, за доли секунды точно, пересчёт по кругу непрерывно. Ячейка по умолчанию снова 3 px, бюджет режима просмотра 10 мс. Настройки сбрасываются (версия 8).

- **0.9.0.** Край круга был ступеньками размером в шаг ячеек: с ячейкой 1 px на круге 120–160 px шаг вырастал до 8 px (ограничение 2500 ячеек), и край шёл ступеньками по 8 px. С 0.9.2 край обрезается по кругу отдельно от ячеек, а в режиме просмотра видно фактический шаг.

- **0.9.2.** Если ячейку приходилось укрупнять (1 px на большом круге), границы цветов и край силуэта шли ступеньками по 4–8 px. С 0.10.0 основа остаётся крупной, а границы уточняются до ячейки из настроек.

- **0.3.0–0.10.0.** Когда круг резко уходил за контур танка, подсветка держалась за контуром и исчезала не сразу: ещё не посчитанные ячейки брали цвет крупного блока над ними, а крупный блок у края танка захватывал и фон; очередь мелких ячеек у края доходила последней. С 0.10.1 цвет крупного блока подставляется только внутри силуэта, а при пересчёте первыми идут блоки на границах.

- **0.10.x.** Настройки открывались только через ModsSettingsAPI: у игрока без него окна не было, мод работал на значениях по умолчанию. С 0.11.0 — своя панель в ангаре (Ctrl+Shift+Y) и свой файл настроек. При резком движении прицела по танку круг на новом месте обрывался, пока не досчитается; с 0.11.0 крупные блоки по всей цели считаются заранее.

- **0.11.0.** Текстовая панель настроек в игре выглядела плохо. С 0.12.0 основное окно снова в ModsSettingsAPI; элемент, которого нет в установленной версии API, заменяется списком, а не ломает всё окно. Панель осталась запасной (Ctrl+Shift+Y). Заранее считались только крупные блоки; с 0.12.0 прогрузка идёт до основы, долю задаёт настройка. Добавлена подпись у прицела: шанс пробития и модули на пути снаряда.

## Решения, отличающиеся от ARMOR_SPEC.md

1. **Отрисовка только поверх экрана** (`GUI.Simple`). Наклейки и обводку не используем (исследование — в истории коммитов 2e299b1 и 369b046).
2. **Обновление каждый кадр** (раздел 2.5): тик через `BigWorld.callback(0, ...)`, расчёт в бюджете кадра из настроек (3 мс по умолчанию). Время пишется в лог сводкой раз в секунду.
3. **Круг вокруг центра прицела фиксированного радиуса вместо круга сведения** (раздел 2.2), по просьбе пользователя; подсветка всей цели — отдельной настройкой. Размер круга сведения не используется. Затемнение при несведённом прицеле (`fadeoffFactorWhenNotAimed`) убрано: `colour` в этом клиенте ненадёжен, а подсветка должна быть видна всегда.
4. **Градиент по вероятности пробития** вместо трёх цветов (раздел 2.4), по просьбе пользователя. Свой цикл по слоям на ванильных данных, см. «Вероятность пробития».
5. **Ячейка 1 px**, каждая ячейка круга (или адаптивная сетка для всей цели) вместо `cellPx = 10` и `maxSamples = 250`.
6. **Без ограничения дальности и затухания по дистанции.** Задержка появления 0.1 с вместо 0.5, показ в движении и в аркаде по умолчанию, цель держится после ухода прицела. Всё настраивается.
7. **Цвет в текстурах** вместо `colour`. Схема для дальтоников из фазы 3 заменена выбором своих цветов.
8. **Настройки в ангаре** — окно ModsSettingsAPI, запасная панель (Ctrl+Shift+Y) и режим просмотра — не было в спецификации. ModsSettingsAPI и ModsList API используются, только если установлены.
9. **Подпись у прицела** с шансом пробития и модулями — не было в спецификации, по просьбе пользователя.
