# BUDGET_SPEC

Спецификация локального приложения учёта бюджета.
Офлайн, без сервера, одна валюта (RUB), сборка в APK через Capacitor.

**Версия документа:** v1.1
**Состав:** Часть 1 — Домен и инварианты · Часть 2 — Расчётный движок · Часть 3 — Экраны · Часть 4 — Хранилище · Часть 5 — Сборка

## Часть 1. Домен и инварианты

### 1.0. Модель учёта

Месяц состоит из двух принципиально разных частей.

**Фиксированный блок.** Зарплата и постоянные платежи. Дат внутри месяца не имеют — считаются одной суммой, привязанной к месяцу целиком.

```
Свободные деньги месяца = Σ постоянных доходов − Σ постоянных расходов
```

**Переменный поток.** Разовые траты с конкретной датой. Записываются вручную. Только они формируют динамику внутри месяца.

```
Итог месяца = Свободные деньги + разовые доходы − переменные траты
```

Из этого следует, чего в модели нет и почему:

| Нет | Почему |
|---|---|
| Дат у постоянных платежей | Единица учёта — месяц. Дата внутри месяца на итог не влияет |
| Переноса с выходных | Следствие предыдущего пункта |
| Схлопывания 31-го числа | То же |
| Подтверждения плановых платежей | Всё вводится руками. Позиция засчитывается в месяц по факту существования |
| Счетов и остатков | Накопление считается как поток за период, не как разница балансов |

---

### 1.1. Общие соглашения

**Деньги.** Целое число копеек.

```ts
type Money = number; // integer, копейки. 1500 ₽ === 150000
```

Никаких `float` в домене и хранилище. Округление только на слое отображения.
Все суммы строго положительные, направление задаётся полем `kind`. Знак в `amount` запрещён — иначе направление кодируется дважды и рано или поздно разъедется.

**Время.** Два разных типа, не взаимозаменяемых.

```ts
type MonthKey = string; // "YYYY-MM" — для фиксированного блока
type DateStr  = string; // "YYYY-MM-DD" — для переменных трат
```

Объекты `Date` в хранилище не попадают. Времени суток нет, поэтому UTC+5 нигде в вычислениях не участвует. Единственное исключение — `createdAt` (ISO 8601 UTC), используется только как tie-breaker при сортировке трат за одну дату.

**Сегодня.** Текущая дата берётся один раз на монтирование экрана и передаётся в расчёты явным параметром. Ни одна функция расчёта не читает системные часы сама — иначе её нельзя протестировать.

**Идентификаторы.** `crypto.randomUUID()`, неизменяемы.

**Удаление.** Сущности, на которые ссылается история, архивируются, а не удаляются.

### 1.2. Category

```ts
interface Category {
  id: string;
  name: string;
  kind: 'INCOME' | 'EXPENSE';
  essential: boolean;   // обязательная vs дискреционная
  defaultFlow: 'ROUTINE' | 'ONE_OFF';   // только для EXPENSE
  icon: string;         // emoji
  color: string;        // hex
  archived: boolean;
  sortOrder: number;
}
```

**Инварианты**

1. `name` после `trim()` непустое, длина ≤ 40.
2. `name` уникально в пределах `kind`, сравнение регистронезависимое.
3. Нельзя удалить, если есть ссылки из `Expense` или `FixedItem`. Вместо удаления — `archived = true`.
4. Архивированная категория не предлагается при вводе, но остаётся в статистике прошлых периодов.
5. `kind` неизменяем после создания.
6. `essential` применим только при `kind === 'EXPENSE'`.
7. `defaultFlow` применим только при `kind === 'EXPENSE'`.

**Два вида переменных трат.**

`ROUTINE` — то, что происходит изо дня в день плавающей суммой: продукты, транспорт, кофе. В постоянные позиции не занести, потому что сумма каждый месяц разная, но сам поток предсказуем.

`ONE_OFF` — то, что изо дня в день не повторяется, но на бюджет влияет: наушники, шина, подарок, поездка.

Различие не косметическое, на нём держится весь расчёт темпа: рутинные траты экстраполируются на месяц, разовые — нет. Иначе покупка за 60 000 третьего числа превращается в прогноз «1 800 000 за месяц».

`defaultFlow` задаётся на категории и подставляется при вводе автоматически. Конкретная операция может его переопределить: обычный обед в кафе — рутина, день рождения на 15 000 в том же кафе — разовое.

**Стартовый набор.** Расходы `ROUTINE`: Продукты, Кафе, Транспорт, Связь, Здоровье. Расходы `ONE_OFF`: Одежда, Техника, Развлечения, Подарки, Прочее. Категории под постоянные позиции: Жильё, Подписки. Доходы: Зарплата, Премия, Прочее.

### 1.3. Expense — переменная операция

Разовая операция с датой. Формирует динамику месяца.

```ts
interface Expense {
  id: string;
  date: DateStr;
  amount: Money;        // > 0
  categoryId: string;
  flow?: 'ROUTINE' | 'ONE_OFF';   // переопределяет defaultFlow категории
  note?: string;        // ≤ 200 символов
  createdAt: string;    // ISO 8601 UTC
}
```

**Инварианты**

1. `amount` — целое, `> 0`.
2. Категория существует (возможно архивированная). Направление операции берётся из `kind` категории — отдельного поля нет, чтобы не было двух источников правды.
3. Операция принадлежит месяцу по полю `date`. `createdAt` в расчётах не участвует никогда.
4. Дата в будущем разрешена. Такая операция входит в итог месяца, но не входит в «потрачено на сегодня» и не участвует в расчёте темпа.
5. Итоговый вид потока: `flow ?? category.defaultFlow`. Поле на операции пустое в подавляющем большинстве случаев — заполняется, только когда подсказка категории явно переопределена.
6. У операций с категорией `kind === 'INCOME'` поток не определён и в расчётах не используется.

Разовый доход (продал что-то, вернули долг) — та же сущность с категорией `kind === 'INCOME'`.

### 1.4. FixedItem — постоянная позиция

Зарплата или постоянный платёж. Даты не имеет, живёт по месяцам.

```ts
interface FixedItemBase {
  id: string;
  title: string;
  kind: 'INCOME' | 'EXPENSE';
  categoryId: string;
  endMonth?: MonthKey;       // последний месяц действия включительно
  note?: string;
  taxPercent?: number;       // 1..99, удержание с дохода. Поля нет — вычета нет
}

type FixedItem =
  | (FixedItemBase & { mode: 'MONTHLY'; amounts: AmountPeriod[] })
  | (FixedItemBase & { mode: 'SPREAD';  spreads: SpreadPeriod[] });

interface AmountPeriod {
  fromMonth: MonthKey;
  amount: Money;             // > 0
}

interface SpreadPeriod {
  fromMonth: MonthKey;       // первый месяц цикла
  totalAmount: Money;        // > 0, сумма платежа целиком
  months: number;            // >= 2, на сколько месяцев размазывается
  payMonth?: MonthKey;       // месяц фактического списания, по умолчанию fromMonth
  payDay?: number;           // 1..31, только для напоминания
}
```

**MONTHLY** — зарплата, аренда, связь. Сумма относится к каждому месяцу как есть.

**SPREAD** — годовые и сезонные платежи: страховка, налог, отпуск. Платёж уходит одной суммой раз в год, но в бюджете учитывается долями, чтобы месяц платежа не проваливался.

Как это выглядит: заводишь «Страховка, 14 500 ₽, раз в год» → приложение делит на 12 и учитывает по 1 208 ₽ в каждом месяце. Когда реально заплатил, вносить ничего не нужно: трата уже учтена двенадцатью кусками.

В интерфейсе `months` задаётся пресетами — раз в год, раз в полгода, раз в квартал — с возможностью ввести произвольное число. Считать месяцы руками пользователь не должен.

Цикл длиной `months` повторяется от `fromMonth`.

`payMonth` и `payDay` в расчётах не участвуют **нигде**. Они существуют только для календаря (3.6): приложение показывает долю, а с карты уйдёт вся сумма, и об этом надо предупредить заранее. Ни одна функция из Части 2, кроме построения календаря, эти поля не читает.

Следствие, которое надо принять осознанно: **фактический платёж отдельной операцией не вносится.** Иначе он посчитается дважды — долями и целиком. В месяц реального списания приложение покажет долю, а не всю сумму, то есть перестанет описывать кошелёк в моменте. За полный цикл арифметика сходится ровно. Для модели без счетов и остатков это последовательно.

**Почему список сумм, а не одно поле.**
Если хранить одну текущую сумму, то повышение аренды с 30 000 до 35 000 задним числом сделает дороже все прошлые месяцы, и вся историческая статистика станет ложной. `amounts` фиксирует, с какого месяца действует какая сумма, и прошлое не переписывается. Альтернатива — снапшот месяца при его закрытии — требует ритуала закрытия и фонового процесса, чего в офлайн-приложении лучше избегать.

**Удержание налога.**

Зарплата обычно называется до вычета, а до кошелька доходит меньше. `taxPercent`
задаёт ставку удержания на конкретной позиции: 13 для НДФЛ, 6 для самозанятости,
своё число для чего угодно ещё. Поля нет — удержания нет, и это состояние
по умолчанию: вычет остаётся возможностью, а не правилом.

```
удержано = round(начислено × taxPercent / 100)
к выплате = начислено − удержано
```

Хранится начисленная сумма, а не сумма к выплате. Иначе правка оклада
и правка удержания разъехались бы: одно число пришлось бы пересчитывать
руками при каждом изменении другого.

Отдельной позицией расхода налог не заводится по той же причине — это дало бы
два числа, которые обязаны меняться синхронно, и первая же правка оклада их
рассинхронизирует.

**Разрешение суммы на месяц M**

```
amountAt(item, M):
  если item.endMonth задан и M > endMonth → позиция не действует

  mode === 'MONTHLY':
    если M < amounts[0].fromMonth → позиция не действует
    иначе → amount последней записи с fromMonth <= M

  mode === 'SPREAD':
    если M < spreads[0].fromMonth → позиция не действует
    p = последняя запись с fromMonth <= M
    i = monthsBetween(p.fromMonth, M) mod p.months   // позиция внутри цикла
    base = floor(p.totalAmount / p.months)
    → i === p.months − 1 ? base + (p.totalAmount − base × p.months) : base
```

Остаток от деления добавляется к последнему месяцу цикла, а не размазывается. Иначе сумма долей не сойдётся с платежом: 14 500 ₽ на 12 месяцев дают 1 208,33 ₽, и за год недобор в 4 копейки. Мелочь, но в спецификации не должно быть мест, где деньги исчезают.

**Инварианты**

1. `amounts` / `spreads` непусты, `fromMonth` уникальны, список отсортирован по возрастанию.
2. Каждый `amount` и `totalAmount` — целое, `> 0`. `months >= 2` и целое.
3. `endMonth`, если задан, `>=` первого `fromMonth`.
4. `kind` совпадает с `kind` категории.
5. `kind`, `categoryId` и `mode` неизменяемы после создания. Смена любого из них сломала бы историю; вместо этого позиция закрывается через `endMonth` и заводится новая.
6. Правка суммы = добавление новой записи с `fromMonth` = месяц, с которого действует. Редактирование существующей записи допустимо только для исправления ошибки ввода и явно помечается в интерфейсе как «исправить, а не изменить с этого месяца».
7. Смена `months` у `SPREAD` — тоже новая запись. Цикл нового периода начинается с её `fromMonth`, старый обрывается там же, даже если не закончился. Это сознательное упрощение: иначе пришлось бы хранить состояние незавершённого цикла.
8. Удаление позиции запрещено, если она действовала хотя бы в одном прошедшем месяце. Вместо этого `endMonth`.
9. `taxPercent`, если задан — целое, `1..99`, и применим только при `kind === 'INCOME'`. С расхода налог не удерживают.

### 1.5. MonthOverride — разовое отклонение

Один месяц выбился из нормы: премию не дали, аренду не платил, заплатил больше.

```ts
interface MonthOverride {
  month: MonthKey;
  fixedItemId: string;
  amount: Money | null;   // null = позиция пропущена в этом месяце
}
```

**Инварианты**

1. Пара `(month, fixedItemId)` уникальна.
2. `amount`, если не `null` — целое, `> 0`.
3. Применяется поверх `amountAt`: сначала разрешается сумма по `amounts`, затем перекрывается оверрайдом.
4. Оверрайд для месяца, в котором позиция не действует, игнорируется.
5. Оверрайд задаёт **начисленную** сумму. Удержание считается от неё, как и в обычном месяце: позиция хранится до вычета, и разовое отклонение хранится так же.

### 1.6. MonthlyTarget — цель по накоплению в месяц

Сколько хочется откладывать каждый месяц. Хранится версионно, как и суммы постоянных позиций: цель меняется — прошлые месяцы сохраняют ту цель, которая действовала тогда.

```ts
interface MonthlyTarget {
  fromMonth: MonthKey;
  amount: Money;      // > 0
}
```

Живёт в `settings.targets: MonthlyTarget[]`.

**Инварианты**

1. `fromMonth` уникальны, список отсортирован по возрастанию.
2. `amount` — целое, `> 0`.
3. Разрешение на месяц — той же функцией, что и `amountAt`: последняя запись с `fromMonth <= M`. Если список пуст или M раньше первой записи — цель не задана, `null`.

Цель — это ориентир для расчёта допустимых трат, а не денежная операция. В `free`, `net` и балансы она не входит.

---

### 1.7. SavingsGoal — цель-накопление

Накопить конкретную сумму на конкретное. Отдельная сущность, не пересекается с `MonthlyTarget`.

```ts
interface SavingsGoal {
  id: string;
  title: string;
  targetAmount: Money;        // > 0
  deadline?: MonthKey;
  contributions: Contribution[];
  archived: boolean;
  createdAt: string;
}

interface Contribution {
  id: string;
  month: MonthKey;
  amount: Money;              // > 0
  note?: string;
}
```

**Взнос в цель — не трата.**
Он не уменьшает `net` и не входит в переменные траты. Отложенные деньги никуда не делись, они просто помечены. Если бы взнос считался расходом, накопление за месяц уменьшалось бы ровно на ту сумму, которую ты накопил, — арифметика стала бы абсурдной.

Следствие: сумма взносов за месяц может превышать `net` этого месяца. Это законно — деньги пришли из накоплений прошлых месяцев. Интерфейс это не считает ошибкой, но подсвечивает.

**Инварианты**

1. `targetAmount` — целое, `> 0`.
2. `deadline`, если задан, `>= месяца создания`.
3. `amount` взноса — целое, `> 0`. Отрицательных взносов нет; изъятие из цели моделируется удалением или правкой взноса.
4. Архивированная цель не показывается в активных, но её взносы остаются в истории.

### 1.8. Корневой документ

```ts
interface BudgetDocument {
  schemaVersion: 4;
  categories: Category[];
  expenses: Expense[];
  fixedItems: FixedItem[];
  overrides: MonthOverride[];
  goals: SavingsGoal[];
  settings: Settings;
}

interface Settings {
  firstMonth: MonthKey;      // с какого месяца ведётся учёт
  startingBalance: Money;    // сколько было накоплено к firstMonth, может быть 0
  targets: MonthlyTarget[];  // версионная цель по накоплению
  forecastMinDay: number;    // с какого дня месяца показывать прогноз, дефолт 5
  oneOffWindow: number;      // окно среднего по разовым в месяцах, дефолт 6
  createdAt: string;
}
```

### 1.9. Сквозные правила

1. Принадлежность месяцу: у `Expense` — по `date`, у `FixedItem` — по разрешению `amountAt`.
2. Итог месяца = `free + разовые доходы − переменные траты`. Не разница остатков: счетов в модели нет.
3. Факт и прогноз разделены на уровне модели и на уровне интерфейса.
4. Правка постоянной позиции и цели по умолчанию действует вперёд, а не назад.
5. Архивированные категории и закрытые позиции из истории не исчезают.
6. Все функции расчёта чистые: на вход документ и дата, на выход число. Системные часы внутри не читаются.

## Часть 2. Расчётный движок

### 2.1. Принципы

Слой расчётов не знает ни про React, ни про хранилище. Вход — `BudgetDocument` и `today: DateStr`, выход — числа. Ни одного обращения к `Date.now()` внутри: любой тестовый кейс воспроизводится подстановкой даты.

Деление встречается ровно в четырёх местах: `savingsRate`, `pace`, `dailyAllowance`, `requiredPerMonth`. Только в них результат не является деньгами. При обратном переводе в деньги — `Math.round`, копейка вниз/вверх роли не играет, но результат обязан остаться целым.

---

### 2.2. Календарные примитивы

```ts
monthKeyOf(date: DateStr): MonthKey        // "2026-03-16" → "2026-03"
dayOfMonth(date: DateStr): number          // "2026-03-16" → 16
daysInMonth(month: MonthKey): number
addMonths(month: MonthKey, n: number): MonthKey
compareMonth(a: MonthKey, b: MonthKey): number
monthRange(from: MonthKey, to: MonthKey): MonthKey[]
```

Реализуются разбором строки, без `new Date()`. Причина: `new Date("2026-03-16")` парсится как UTC, а `new Date(2026, 2, 16)` — как локальное время, и смешение этих двух путей даёт сдвиг на сутки. Разбор строки этот класс багов исключает целиком.

Високосный год: `(y % 4 === 0 && y % 100 !== 0) || y % 400 === 0`.

---

### 2.3. Разрешение фиксированного блока

```ts
resolveFixed(doc: BudgetDocument, month: MonthKey): ResolvedFixed[]

interface ResolvedFixed {
  itemId: string;
  title: string;
  kind: 'INCOME' | 'EXPENSE';
  categoryId: string;
  amount: Money;              // к выплате: gross − tax, участвует в расчётах
  gross: Money;               // начислено. Без вычета совпадает с amount
  tax: Money;                 // удержано. 0, если вычет не включён
  overridden: boolean;
  isReserve: boolean;         // mode === 'SPREAD'
}
```

Алгоритм:

1. Для каждой `FixedItem` вычислить `amountAt(item, month)`. Позиция не действует — пропустить.
2. Найти `MonthOverride` по ключу `${month}:${itemId}`.
3. Оверрайд с `amount === null` — позиция исключается из месяца.
4. Оверрайд с числом — сумма заменяется, `overridden = true`.

```
fixedIncome      = Σ amount где kind === 'INCOME'    // после удержаний
fixedIncomeGross = Σ gross  где kind === 'INCOME'    // до удержаний
taxWithheld      = Σ tax    где kind === 'INCOME'
fixedExpense     = Σ amount где kind === 'EXPENSE'
reserved         = Σ amount где isReserve            // доля годовых внутри fixedExpense
free             = fixedIncome − fixedExpense
```

`taxWithheld` не расход: эти деньги до кошелька не доходили, и в `fixedExpense`
им делать нечего. Величина существует только ради интерфейса — показать,
из чего сложилась разница между «начислено» и «пришло».

`reserved` — не отдельные деньги, а часть `fixedExpense`. Выделяется, чтобы в интерфейсе было видно: «из 37 000 постоянных 2 400 — резерв на годовые платежи».

`free` может быть отрицательным (месяц без зарплаты, дорогой месяц). Модель это допускает, интерфейс обязан показывать честно.

Оверрайды индексируются в `Map` один раз при загрузке документа.

### 2.4. Переменный поток

```ts
expensesOfMonth(doc, month): Expense[]
```

Индекс `Map<MonthKey, Expense[]>` строится при загрузке и поддерживается при мутациях. Внутри месяца сортировка по `(date, createdAt)`.

```
routineExpense(month)  = Σ amount где flow === 'ROUTINE'
oneOffExpense(month)   = Σ amount где flow === 'ONE_OFF'
variableExpense(month) = routineExpense + oneOffExpense
variableIncome(month)  = Σ amount где категория INCOME

routineToDate(month)   = routineExpense, только date <= today
oneOffToDate(month)    = oneOffExpense,  только date <= today
```

Операции с датой в будущем входят в месячные суммы, но не в `...ToDate` и не в расчёт темпа. Иначе одна запланированная покупка мгновенно ломает дневной темп.

Отсюда же берётся **стоимость жизни**: `fixedExpense + routineExpense`. Это минимум, в который месяц обходится независимо от разовых решений.

### 2.5. MonthSummary

```ts
interface MonthSummary {
  month: MonthKey;
  isCurrent: boolean;

  fixedIncome: Money;
  fixedExpense: Money;
  reserved: Money;              // часть fixedExpense, доли годовых платежей
  free: Money;                  // fixedIncome − fixedExpense

  variableIncome: Money;
  routineExpense: Money;
  oneOffExpense: Money;
  variableExpense: Money;       // routine + oneOff
  routineToDate: Money;         // только для текущего месяца
  oneOffToDate: Money;

  costOfLiving: Money;          // fixedExpense + routineExpense
  monthCost: Money;             // costOfLiving + oneOffExpense — факт этого месяца
  totalIncome: Money;           // fixedIncome + variableIncome
  net: Money;                   // free + variableIncome − variableExpense
  savingsRate: number | null;   // net / totalIncome, null если totalIncome === 0
}
```

`savingsRate` может быть отрицательным. Это не ошибка, это перерасход.

### 2.6. Динамика внутри месяца

```ts
cumulativeByDay(doc, month, today): (Money | null)[]
```

Длина массива = `daysInMonth(month)`. Элемент с индексом `i` — сумма трат с `dayOfMonth <= i + 1`.

Кривая строится **только по рутинным тратам**. Разовые покупки и разовые доходы выносятся отдельными метками на той же оси. Причина та же, что и в расчёте темпа: одна покупка за 60 000 даёт вертикальную ступеньку, после которой форма кривой перестаёт что-либо говорить о том, как идут обычные траты.

Для текущего месяца элементы после сегодняшнего дня — `null`, а не ноль. Ноль означал бы «в этот день не тратил», `null` — «день ещё не наступил». Это разные вещи, и на графике они рисуются по-разному.

### 2.7. Сравнение с прошлым месяцем

```ts
compareToPrevious(doc, month, today): MonthComparison

interface MonthComparison {
  cutoffDay: number;
  current: Money;
  previous: Money | null;
  previousTruncated: boolean;
  delta: Money | null;          // current − previous
  deltaPct: number | null;
}
```

`cutoffDay` — для текущего месяца номер сегодняшнего дня, для прошедшего — число дней в нём.

Обе кривые обрезаются по одному и тому же номеру дня и строятся по рутинным тратам. Неполный месяц никогда не сравнивается с полным — иначе 16 марта всегда будет выглядеть как экономия относительно целого февраля. Разовые покупки сравниваются отдельной цифрой, без разбивки по дням.

Граничные случаи:

- В прошлом месяце дней меньше `cutoffDay` (31 марта против февраля) — берётся значение последнего дня, `previousTruncated = true`. В интерфейсе помечается.
- Прошлого месяца нет в истории (`month === settings.firstMonth`) — `previous = null`, блок сравнения скрывается.
- `previous === 0` — `deltaPct = null`, показывается только абсолютная дельта. Деление на ноль не маскируется бесконечностью.

### 2.8. Темп и прогноз

Считается только для текущего месяца. Для прошедших есть факт, прогноз в них бессмыслен.

```
day             = dayOfMonth(today)
routinePace     = routineToDate / day                 // копеек в день
routineForecast = Math.round(routinePace × daysInMonth(month))
forecast        = routineForecast + oneOffExpense(month)
netForecast     = free + variableIncome − forecast
```

Экстраполируется только рутинный поток. Разовые траты добавляются как есть, полной суммой за месяц, включая уже записанные операции с будущей датой: они известны и повторяться не будут.

**Обычный темп.** Ориентир, с которым сравнивается текущий месяц.

```
dailyRoutine(M) = routineExpense(M) / daysInMonth(M)
usualDaily      = медиана dailyRoutine по последним 6 полным месяцам
potentialExtra  = (routinePace − usualDaily) × daysLeft
```

Здесь медиана, а не среднее — и это сознательно противоположно решению в анализе разовых (2.12). Там выброс это деньги, которые пришлось заплатить, и он обязан войти в оценку. Здесь выброс это поведение: месяц с переездом или отпуском не должен поднимать планку, иначе её станет слишком легко перебивать и она перестанет что-либо значить.

`potentialExtra` показывается только когда выполнено всё сразу: цель по текущему прогнозу закрывается, `routinePace > usualDaily`, и полных месяцев в истории не меньше трёх. Иначе подсказка либо давит на того, кто и так не укладывается, либо сравнивает с пустотой.

**Порог достоверности.** При `day < settings.forecastMinDay` (дефолт 5) прогноз не показывается. Второго числа одна крупная покупка умножается на 30 и даёт цифру, которая пугает без всякого основания. Скрыть честнее, чем показать с оговоркой.

### 2.9. Вписываемся ли в цель

```ts
targetStatus(doc, month, today): TargetStatus | null   // null если цель не задана

interface TargetStatus {
  target: Money;              // цель по накоплению на месяц
  budget: Money;              // free + variableIncome − target
  spent: Money;               // routineToDate + oneOffToDate
  committed: Money;           // spent + разовые с датой позже сегодня
  remaining: Money;           // budget − committed
  daysLeft: number;           // daysInMonth − day + 1, сегодня включительно
  dailyAllowance: Money | null;
  state: 'IMPOSSIBLE' | 'BROKEN' | 'AT_RISK' | 'ON_TRACK' | 'AHEAD';
}
```

`budget` — сколько можно потратить за месяц, чтобы цель выполнилась.

```
dailyAllowance = daysLeft > 0 ? Math.round(remaining / daysLeft) : null
```

Состояния разрешаются в этом порядке:

| Состояние | Условие | Смысл |
|---|---|---|
| `IMPOSSIBLE` | `budget <= 0` | Цель недостижима даже при нулевых тратах: постоянные платежи съедают всё |
| `BROKEN` | `committed > budget` | Уже перетрачено или обещано, в этом месяце цель не выполнить |
| `AT_RISK` | `forecast > budget` | По текущему темпу не уложишься |
| `AHEAD` | `forecast <= budget × 0.9` | Идёшь с запасом |
| `ON_TRACK` | иначе | Укладываешься |

Если прогноз ещё не показывается (`day < forecastMinDay`), `AT_RISK` и `AHEAD` не вычисляются: остаются `IMPOSSIBLE`, `BROKEN` и `ON_TRACK`.

### 2.10. Прогресс цели-накопления

```ts
goalProgress(goal, today): GoalProgress

interface GoalProgress {
  saved: Money;                       // Σ взносов
  remaining: Money;                   // max(0, targetAmount − saved)
  pct: number;                        // saved / targetAmount, может быть > 1
  monthsLeft: number | null;          // до deadline включительно
  requiredPerMonth: Money | null;     // remaining / monthsLeft
  avgPerMonth: Money | null;          // по фактическим взносам
  projectedMonths: number | null;     // remaining / avgPerMonth
  onSchedule: boolean | null;
}
```

`monthsLeft` считается от текущего месяца включительно. Если `deadline` уже прошёл, `monthsLeft = 0`, `requiredPerMonth = null`, цель помечается просроченной.

`avgPerMonth` берётся по месяцам, в которых были взносы, а не по всем месяцам с момента создания цели. Иначе один пропущенный месяц занижает средний темп вдвое.

annualCalendar(doc, fromMonth, horizon = 12): CalendarMonth[]

interface CalendarMonth {

Календарь ничего не добавляет к суммам месяца и ни на что не влияет. Он отвечает на единственный вопрос: в каком месяце и сколько уйдёт одним куском. Без него размазывание превращается в ловушку — бюджет показывает 1 200, а в марте с карты исчезает 14 400.

### 2.12. Анализ разовых трат

Разовые траты рваные по природе: в феврале ноль, в марте 24 000. Прямая дельта месяц к месяцу на таком ряде даёт бессмысленный ответ — «+∞%» или «−100%». Поэтому месяцы показываются столбцами, а базой для оценки служит скользящее среднее.

```ts
oneOffAnalysis(doc, month, today, window = 6): OneOffAnalysis

interface OneOffAnalysis {
  current: Money;
  count: number;
  avg: Money | null;            // скользящее среднее за window полных месяцев
  delta: Money | null;          // current − avg
  deltaPct: number | null;
  byMonth: { month: MonthKey; amount: Money; count: number }[];
  topCategories: { categoryId: string; amount: Money; count: number }[];
  monthIncomplete: boolean;
  insufficientHistory: boolean; // полных месяцев в истории меньше 3
}
```

**Среднее, а не медиана.** Медиана устойчивее к выбросам, но выброс здесь — не шум, а реальные деньги, которые пришлось заплатить. Для планирования нужна средняя нагрузка, и она обязана учитывать дорогие месяцы.

**Текущий месяц в окно не входит**, иначе он сравнивается сам с собой.

**Обрезка по дню здесь не применяется.** Рутина распределена по месяцу более-менее равномерно, разовые — нет: покупка 28-го числа так же вероятна, как 3-го. Обрезка создала бы ложную точность. Вместо неё выставляется `monthIncomplete = true`, и интерфейс показывает, что месяц ещё идёт.

При истории меньше 3 полных месяцев `avg = null`, блок сравнения скрывается.

**Типичный месяц**

```
typicalMonthCost = costOfLiving + oneOffAvg
```

Это оценка, и её нельзя путать с `monthCost` из `MonthSummary`. Разница принципиальная:

| | Что входит | На какой вопрос отвечает |
|---|---|---|
| `monthCost` | постоянные + рутина + разовые **этого** месяца | Сколько мне стоил март |
| `typicalMonthCost` | постоянные + рутина + **средние** разовые | Сколько мне нужно в месяц вообще |

`monthCost` — факт, считается по каждому месяцу отдельно, ничего не усредняется. `typicalMonthCost` — прогнозная величина, и именно она идёт в расчёт запаса прочности: постоянные с рутиной дают минимум, но минимумом жизнь не ограничивается, что-то разовое случается почти каждый месяц.

**Запас прочности**

```
accumulated = settings.startingBalance + Σ net по всем месяцам с firstMonth
runwayMonths = typicalMonthCost > 0 ? accumulated / typicalMonthCost : null
```

`accumulated` — не остаток на счетах, а накопленное с начала учёта плюс стартовая сумма, которую пользователь ввёл сам. Приложение не знает про его реальные счета и не должно делать вид, что знает. В интерфейсе цифра подписывается как «по данным учёта».

---

### 2.13. Агрегация по кварталам и годам

Период — список месяцев. Все суммы складываются помесячно, ничего не пересчитывается заново.

```
Σ free, Σ net, Σ variableExpense по месяцам периода
savingsRate периода = Σ net / Σ totalIncome
```

Средняя ставка накопления за период — отношение сумм, а не среднее арифметическое месячных ставок. Среднее из процентов даёт неверный ответ при разных доходах: месяц с доходом 0 и ставкой −200% утянет среднее вниз непропорционально своему весу.

Незавершённый месяц входит в квартал по факту на сегодня и помечается как неполный.

### 2.14. Тестовые кейсы

Суммы в рублях для читаемости, внутри — копейки.

**К1. Базовый месяц.** Зарплата 120 000 с 2026-01. Аренда 35 000, связь 800, подписки 1 200. Март 2026, переменных трат на 28 400.

```
fixedIncome 120 000 · fixedExpense 37 000 · free 83 000
net 54 600 · savingsRate 0.455
```

**К2. Повышение суммы не переписывает прошлое.** Аренда `amounts: [{2026-01, 35 000}, {2026-06, 40 000}]`.

```
amountAt(2026-05) → 35 000
amountAt(2026-06) → 40 000
amountAt(2025-12) → не действует
```

**К3. Оверрайды.** Март: премия 20 000 не пришла → `{2026-03, премия, null}` → `fixedIncome` без неё. Апрель: аренда разово 37 000 → `{2026-04, аренда, 37 000}`, май снова 35 000.

**К4. Темп и сравнение.** Сегодня 2026-03-16, рутинных трат 28 400, разовых нет.

```
routinePace 1 775/день · routineForecast 1 775 × 31 = 55 025
forecast 55 025
февраль на 16-е число, рутина 31 200 → delta −2 800, −8.97%
```

**К5. Цель.** Цель 40 000 в месяц, условия К1 и К4.

```
budget 83 000 − 40 000 = 43 000
spent 28 400 · committed 28 400 · remaining 14 600
daysLeft 16 · dailyAllowance 913
forecast 55 025 > 43 000 → AT_RISK
```

**К6. Недостижимая цель.** free 30 000, цель 40 000 → `budget = −10 000` → `IMPOSSIBLE` независимо от трат.

**К7. Февраль против марта.** Сегодня 2026-03-31, `cutoffDay = 31`, в феврале 28 дней → берётся 28-й день, `previousTruncated = true`.

**К8. Взнос больше накопления.** net месяца 54 600, взнос в цель 80 000. Законно, `net` не меняется, интерфейс подсвечивает.

**К9. Разовая покупка не ломает прогноз.** Условия К4, плюс 3 марта наушники за 24 000 с `flow: ONE_OFF`.

```
routineToDate 28 400 → routinePace 1 775 → routineForecast 55 025
oneOffExpense 24 000
forecast 79 025
```

Если бы та же покупка попала в рутину: `pace 3 275 → forecast 101 525`. Расхождение 22 500 взялось бы из ниоткуда.

**К10. Размазанный годовой платёж.** Страховка 14 500 ₽, `mode: SPREAD`, `fromMonth 2026-01`, `months 12`.

```
base = floor(1 450 000 / 12) = 120 833 коп = 1 208,33 ₽
январь…ноябрь → 1 208,33 · декабрь → 1 208,37
Σ за цикл = 14 500,00 ровно
2027-01 → новый цикл, снова 1 208,33
```

**К11. Разовые против среднего.** Разовые по месяцам: окт 0, ноя 24 000, дек 3 500, янв 41 000, фев 0, мар 12 000. Текущий апрель — 24 000.

```
avg за 6 месяцев = 80 500 / 6 = 13 417
delta +10 583 · deltaPct +78,9%
```

### 2.15. Открытые вопросы

- Нужен ли учёт долгов и рассрочек. Сейчас рассрочка моделируется как `FixedItem` с `endMonth` — этого хватает для платежей, но не показывает остаток долга.
- Первый месяц учёта может быть неполным: если начать 20 марта, март занизит и медиану темпа (2.8), и среднее по разовым (2.12). Сейчас он участвует в окнах наравне с остальными. Вариант — исключать `firstMonth` из всех скользящих окон.

## Часть 3. Экраны

### 3.1. Навигация

Нижней панели вкладок нет. Переходы идут через шторку слева, которую открывает бургер в левом верхнем углу.

- Бургер 16×16, внешние границы полосок образуют квадрат.
- Шторка занимает 70% ширины (максимум 250 px), тянется на всю высоту, тёмная.
- Пункты сверху вниз: **Домой**, **Расходы**, **Цели**, **Дашборды**.
- Внизу шторки, отделённая линией: **Настройки**, а рядом с ними — кнопка переключения темы. Тема меняется в один тап, без захода в настройки: это то, что переключают по времени суток, а не настраивают раз и навсегда.
- На «Расходах» и «Дашбордах» рядом с бургером стоит стрелка назад — она ведёт сразу на главную, а не на предыдущий экран.
- Внутри раскрытого дашборда стрелка возвращает к списку дашбордов. Это единственное место, где она значит не «домой».

Узкая полоса с одними иконками, без подписей, отвергнута: иконка монеты без подписи читается как «доходы», а не «добавить трату».

---

### 3.2. Главная

Шапка: бургер, месяц, сегодняшнее число справа. Месяц листается свайпом, дальше `firstMonth` назад и дальше текущего вперёд навигация не идёт.

Блоки сверху вниз:

**1. Бюджет месяца.** Прямоугольник со скруглением 28, текст белый. Крупно — **сколько осталось**: весь доход месяца минус всё потраченное, включая постоянные. Это в точности `net` месяца, отдельной величины не заводится. Мелко в подвале — весь бюджет и цель, а при включённом удержании ещё и удержанная сумма.

**Сам блок и есть шкала**, как индикатор заряда: залитая часть — то, что осталось, тёмная — потраченное. Доля заливки это `net / totalIncome`, то есть ровно ставка накопления из 2.5, и по мере трат она уходит вправо.

Разряженная часть тёмная, а не бледная: белые подписи должны читаться и на ней. По той же причине градиент развёрнут глубоким тоном влево — текст стоит слева и на светлом конце расплывался бы. Градиент лежит на всю ширину блока и только подрезается справа: иначе он сжимался бы вместе с заливкой и менял цвет под текстом на месте.

**Риска цели** отмечает `target / total` — долю шкалы, которую нужно оставить нетронутой. Заливка выше риски означает, что цель ещё закрывается, ниже — что уже нет, и это ровно та же граница, на которой блок краснеет. По высоте цифры риска приглушена, чтобы не резать число пополам, и остаётся сплошной только засечками сверху и снизу.

Градиент блока меняется по тому, как остаток стоит против цели:

| Состояние | Условие | Градиент |
|---|---|---|
| `SAFE` | остатка заметно больше цели | `#22C46E → #06834A` |
| `NEAR` | сверх цели осталось меньше 15% | `#F2A23C → #C2701A` |
| `SHORT` | остатка меньше цели | `#E2554A → #9E2A22` |

Цель не задана — сравнивать не с чем: блок зелёный, и краснеет только при перерасходе, когда остаток ушёл ниже нуля. Ниже нуля шкала не опускается: пустая полоса и есть худшее, что она показывает.

Блок нажимается и открывает шторку дохода: список постоянных доходов с суммами, правка суммы тем же диалогом из 3.4 и переключатель удержания налога на каждой позиции. Доход правят чаще, чем заводят, и ради этого не должно приходиться идти в настройки. Разовые доходы показаны там же списком, но правятся в истории: у них есть дата, а значит место им среди операций.

Зелёный взят глубже, чем на черновике: на светлом белые подписи расплывались. Блок остаётся ярким, но 12-пиксельный текст на нём читается.

**2. Три микро-окна** в ряд, скругление 16:

| Окно | Значение | Подпись |
|---|---|---|
| Потрачено | `monthCost` | из всего бюджета |
| Трачу в день | `routinePace` | обычный темп |
| Разовые | `oneOffExpense` | за месяц |

Потраченное и остаток в блоке бюджета в сумме дают весь доход: два числа
на экране описывают одну шкалу с разных концов, и сойтись они обязаны.

**Правило красного.** Число в «Трачу в день» становится приглушённо-красным (`#D8453C`), когда `forecast > budget`, то есть текущий темп пробивает потолок до цели. Цвет приглушённый, не сигнальный: это замечание, а не авария.

Цвет на главной меняют только это число и шкала бюджета, и говорят они о разном: число про темп, шкала про остаток от дохода. Совпадать они не обязаны — можно идти быстрее обычного и всё ещё иметь запас.

**3. Карточка «До цели».** Заголовок, справа `remaining`. Ниже полоса: заливка `committed / budget`, на полосе метка положения, в котором следовало бы находиться при ровном темпе к сегодняшнему дню. Разрыв между заливкой и меткой читается без цифр. Полоса краснеет вместе с дневным числом.

Под полосой — одна из трёх подсказок:

- **Не укладываешься:** на сколько выйдет месяц по текущему темпу, каков потолок, на сколько мимо цели и сколько держать в день, чтобы вернуться.
- **Укладываешься, но тратишь больше обычного:** обычный темп, текущий темп и сколько отложится сверху при возврате к обычному. Условия показа — в 2.8.
- **Укладываешься с запасом:** сколько можно тратить в день и всё равно закрыть цель.

**4. Разбивка.** Три разворачивающиеся строки и итог:

```
› Постоянные   5 позиций, резерв 1 200      37 000
› Рутина       27 трат за 16 дней           28 400
› Разовые      3 покупки                    12 000
  Потрачено всего   с постоянными           77 400
```

Тап разворачивает строку вниз. Постоянные показывают все позиции, включая долю годовых с подписью «14 400 ₽ в год». Рутина показывает шесть последних и кнопку перехода в историю. Разовые показывают все.

Числительные склоняются: «5 позиций», а не «5 позиции».

**5. Кнопка добавления.** Прижата к низу, на всю ширину, высота 56, скругление 20, синяя `#1C6BFF`, белый плюс по центру. Ведёт на «Расходы», вкладка «Добавить».

### 3.3. Расходы

Одна страница, две вкладки: **Добавить** и **История**. Разносить их по разным пунктам меню незачем — это одно дело.

#### Вкладка «Добавить»

Пять панелей, помещаются в экран целиком. Прокрутки здесь нет: выбор из пяти пунктов не должен требовать мотания.

| Панель | Стиль |
|---|---|
| Разовая трата | сплошная синяя |
| Рутинная трата | сплошная синяя |
| Постоянный платёж | контурная |
| Годовой платёж | контурная |
| Взнос в цель | контурная |

Сплошным выделены два ежедневных действия, контурным — то, что заводится раз и надолго.

Тап по «разовой» или «рутинной» поднимает шторку быстрого ввода. Остальные три открывают свои формы.

#### Шторка быстрого ввода

Поднимается снизу, верх экрана остаётся виден. Состав: сумма с сразу открытой цифровой клавиатурой, ряд чипов категорий по частоте за 30 дней, переключатель «Рутина / Разовое», кнопка сохранения. Дата по умолчанию сегодня, меняется тапом. Заметка свёрнута.

**Переключатель стоит в том значении, с какой панели пришли, и подсказка категории его не перебивает.** Выбор панели — заявление пользователя, `defaultFlow` — догадка приложения, и догадка тут не главнее. Иначе «разовая трата» с категорией «Кафе» молча становилась бы рутиной — ровно в том случае из 1.2, ради которого поток и переопределяют.

`defaultFlow` от этого не перестаёт работать: он решает, попадёт ли поле `flow` в операцию вообще. Совпало с подсказкой — поля нет и вид берётся из категории, разошлось — поле пишется (1.3, инвариант 5).

Типичная трата вносится двумя действиями: сумма и чип категории.

Защита от дублей: если за последние две минуты сохранена операция с той же суммой и категорией, шторка спрашивает подтверждение.

#### Вкладка «История»

- Фильтры: **Все**, **Постоянные**, **Рутина**, **Разовые**. Сумма по текущему фильтру — в шапке.
- Постоянные идут отдельным блоком сверху, пунктирной рамкой, без дат: это доля месяца, а не трата конкретного дня.
- Переменные операции сгруппированы по дням, в заголовке дня — сумма дня.
- Тап по строке раскрывает действия. Одновременно раскрыта только одна строка.
- Разреза по категориям нет. Категориям место в дашбордах, а список нужен для правки конкретной операции.

**Действия и что они значат в модели**

| Кнопка | Где | Что делает | Модель |
|---|---|---|---|
| Изменить | трата | правка суммы, категории, даты, вида потока | правка `Expense` |
| Удалить | трата | убирает операцию | удаление `Expense` |
| Изменить | постоянный | открывает карточку позиции | см. 3.4 |
| Пропустить | постоянный | только этот месяц, в следующем платёж вернётся | `MonthOverride` с `amount: null` |
| Удалить | постоянный | больше не плачу, с этого месяца и дальше | `endMonth` = предыдущий месяц |

**Удаление постоянной позиции не стирает прошлое.** Если снести аренду задним числом, январь покажет на 32 000 больше накоплений, чем было, и все графики соврут. Поэтому удаление действует с текущего месяца вперёд. Позиция, не действовавшая ни в одном прошедшем месяце, удаляется полностью — терять нечего.

Стереть и прошлое тоже можно, но это отдельное действие в карточке позиции под именем «исправить ошибку», с предупреждением.

**Отмена.** После любого удаления или пропуска снизу всплывает полоса с кнопкой «Вернуть» на 4,5 секунды. Подтверждающих диалогов на этих действиях нет — отмена дешевле вопроса.

---

### 3.4. Карточка постоянной позиции

Открывается кнопкой «Изменить». Название, категория, сумма, для годовых — сумма за год и доля месяца.

Правка суммы предлагает два варианта, первый выбран по умолчанию:

- **Изменить с апреля** — новая запись в `amounts`, прошлые месяцы не трогаются.
- **Исправить ошибку** — правка текущей записи, с подписью, что это пересчитает уже закрытые месяцы.

Формулировки именно такие, без слова «редактировать»: пользователь выбирает между смыслами, а не между режимами. То же самое диалоговое окно используется для цели по накоплению в настройках.

---

### 3.5. Дашборды

Вертикальный список карточек, листается вниз.

- Карточка на **белом** фоне, скругление 22, высота превью 158.
- Внутри — живой предпросмотр графика, не картинка.
- Подпись снизу поверх градиента от прозрачного к `rgba(6,16,11,.82)`. Градиент гаснет чуть выше заголовка, только ради читаемости белого текста.
- Подписи месяцев в превью не рисуются — они попадали бы под затемнение. В раскрытом дашборде они есть.

Пять дашбордов:

1. **Накопление по месяцам** — столбцы, минус вниз.
2. **Темп месяца** — кривая рутины по дням, пунктиром прошлый месяц, точками разовые покупки.
3. **Структура трат** — составные столбцы: постоянные, рутина, разовые.
4. **Разовые и среднее** — столбцы месяцев и линия скользящего среднего.
5. **Запас прочности** — на сколько хватит накопленного.

Раскрытый дашборд: крупная цифра, подпись, большой график, легенда, переключатель периода месяц / квартал / год.

**Цвета линий.** Зелёный `#00D26A`, красный `#FF2D62`, серый `#D5DED8` для прошлого периода и нейтральных долей. Кислотный неон с тёмного фона отвергнут: на белом он нечитаем, а делать дашборды тёмными ради него значит разрывать приложение надвое.

---

### 3.6. Календарь годовых

Открывается из «Расходов», вкладка «История», фильтр «Постоянные» — ссылкой под блоком постоянных платежей.

Список на 12 месяцев вперёд от текущего. Месяц со списанием выделен рамкой и суммой целиком, остальные показаны прочерком. Внизу — пояснение, что в бюджете эти платежи уже учтены долями.

Экран существует ради одной проблемы: приложение честно показывает 1 200 ₽ в месяц, а в марте с карты уходит 14 400. Без календаря размазывание годовых из удобства превращается в ловушку.

---

### 3.7. Цели

Список: название, полоса прогресса, накоплено из целевого, требуемый темп до срока.

Экран цели: график взносов по месяцам, фактический средний темп против требуемого, кнопка «внести».

Если сумма взносов за месяц превышает `net` этого месяца, показывается пояснение, что взнос покрыт накоплениями прошлых месяцев. Это не ошибка и не блокируется.

Просроченная цель не удаляется и не прячется: показывается с непройденной датой и предложением сдвинуть срок.

---

### 3.8. Настройки

Цель по накоплению в месяц (диалог из 3.4), стартовая сумма накоплений, первый месяц учёта, день начала показа прогноза, окно среднего по разовым, категории с их видом потока по умолчанию, экспорт и импорт файла.

### 3.9. Визуальный язык

| Токен | Значение | Где |
|---|---|---|
| `--paper` | `#F1F4F1` | фон экрана |
| `--card` | `#FFFFFF` | карточки |
| `--ink` | `#0E1511` | основной текст |
| `--muted` | `#6B7A70` | подписи |
| `--line` | `#DFE6E0` | границы |
| `--green-a` / `--green-b` | `#22C46E` / `#06834A` | блок бюджета |
| `--blue` | `#1C6BFF` | всё, что добавляет |
| `--alarm` | `#D8453C` | превышение |
| `--acid-green` / `--acid-red` | `#00D26A` / `#FF2D62` | линии графиков |
| `--warn-a` / `--warn-b` | `#F2A23C` / `#C2701A` | шкала подошла к цели |
| `--short-a` / `--short-b` | `#E2554A` / `#9E2A22` | остатка меньше цели |

Тёмная тема переопределяет весь набор, кроме зелёного, синего и цветов линий: они одинаково работают на обоих фонах. Цвет подложки графиков и сетки — токены, а не константы в коде рисования, иначе при смене темы графики останутся белыми.

**Шрифт** — Golos Text, он рисовался под русский интерфейс. Цифры табличные (`tabular-nums`), иначе суммы в столбце пляшут.

**Скругления разные по уровням, а не одно на всё:** блок бюджета 28, карточки 20, микро-окна 16, строки списка 14, кнопки 11–20.

**Синий значит добавление, зелёный — деньги, красный — превышение, оранжевый — предупреждение.** Больше цветов в интерфейсе нет.

Оранжевый добавлен ради одной вещи — шкалы бюджета, где нужна ступень между «всё хорошо» и «уже нет». Больше нигде он не появляется: два состояния вместо трёх на этой шкале означали бы, что красный загорается внезапно, без предупреждения.

### 3.10. Правила отображения

- Копейки только при вводе и правке. В списках и графиках — целые рубли.
- Крупные суммы не сокращаются до «83k». Ошибка чтения стоит дороже сэкономленного места.
- Отрицательные — со знаком минус и цветом, не в скобках.
- Прогноз визуально отличается от факта всегда. Смешивать их в одном числе запрещено.
- Пустые состояния показывают, что сделать, а не нули.
- Диалоги подтверждения — только на необратимом. Обратимое отменяется полосой внизу.
- Ничего не блокируется из-за странных данных: отрицательные свободные, взнос больше накопления, ставка накопления −40% показываются как есть.
- Числительные склоняются везде.

---

### 3.11. Первый запуск

Три шага, каждый пропускается: зарплата, постоянные платежи с пресетами, цель по накоплению. Пропустивший всё получает рабочее приложение, дашборд ведёт к нужному экрану. Онбординг не повторяется и вызывается из настроек.

---

### 3.12. Открытые вопросы

- Виджет на домашний экран с остатком на день. Требует нативного слоя поверх Capacitor, объём работы несопоставим с остальным приложением.
- Должна ли тема при первом запуске браться из системной, а переключатель уже отклонять её вручную. Сейчас переключатель самостоятельный.
- Нужно ли напоминание за несколько дней до годового списания. Для этого понадобится `payDay` и уведомления, то есть нативный слой.

## Часть 4. Хранилище

### 4.1. Где лежат данные

Один JSON-файл `budget.json` в приватной директории приложения (Capacitor Filesystem, `Directory.Data`). Рядом папка `backups/`.

Приватная директория не видна в файловом менеджере и галерее и вычищается при удалении приложения. Отсюда обязательность экспорта: переустановка сносит всё, и пользователь должен об этом узнать до того, как это случится, а не после.

**Почему не SQLite.** Пять лет учёта это около 12 000 операций и порядка 2 МБ JSON. Парсинг занимает десятки миллисекунд, агрегация — единицы. Нативный плагин добавил бы сборочные сложности ради объёма, который свободно помещается в память.

**Почему не Preferences.** Это key-value для мелких настроек, а не для растущего документа.

---

### 4.2. Формат файла

```json
{
  "format": "budget-app",
  "savedAt": "2026-03-16T18:42:11Z",
  "appVersion": "1.0.0",
  "doc": { "schemaVersion": 3, "categories": [], "expenses": [] }
}
```

Конверт несёт только метаданные. `schemaVersion` живёт внутри `doc` и **не дублируется** в конверте: два места для одного числа рано или поздно разойдутся.

`format` — магическая строка. Без неё импорт любого постороннего JSON проходил бы первую проверку и падал где-то глубже, уже непонятно почему.

Кодировка UTF-8 без BOM. Рабочий файл пишется без отступов, экспортный — с отступами: его может открыть человек.

---

### 4.3. Атомарная запись

`Filesystem.writeFile` не атомарен. Обрыв на середине — убитый процесс, разряженная батарея — оставит обрезанный файл, а это вся история целиком.

Порядок записи:

1. Сериализовать документ в строку.
2. Записать в `budget.tmp`.
3. Прочитать `budget.tmp` обратно и сверить длину. Файл маленький, проверка дешёвая.
4. `rename budget.tmp → budget.json` — переименование в пределах одной файловой системы атомарно.

Если шаг 3 не сошёлся, `budget.tmp` удаляется, `budget.json` остаётся нетронутым, пользователь получает сообщение. Промежуточного состояния, в котором основной файл испорчен, не существует ни на одном шаге.

**Когда пишем.** Не на каждый тап: дебаунс 800 мс после последнего изменения, плюс принудительная запись по событию `pause` (приложение уходит в фон) и перед экспортом. В памяти держится флаг несохранённых изменений.

---

### 4.4. Бэкапы

Перед записью, но не чаще раза в сутки, текущий `budget.json` копируется в `backups/YYYY-MM-DD.json`. Хранятся семь последних, старые удаляются.

Снимок суточный, а не на каждую запись: две сотни операций за день дали бы две сотни копий почти одинакового состояния. Суточный снимок закрывает реальный сценарий — «вчера что-то сломал, хочу как было».

Восстановление живёт в настройках: список снимков с датой и размером. Восстановление заменяет текущий документ и потому требует подтверждения — это то самое необратимое действие, ради которого диалоги вообще существуют.

---

### 4.5. Экспорт и импорт

**Экспорт** — тот же JSON с отступами, через системный Share Sheet или сохранение в `Documents`. Имя `budget-2026-03-16.json`.

**Импорт** — выбор файла и проверки строго по порядку:

1. Валидный JSON.
2. `format === "budget-app"`.
3. `schemaVersion` не выше поддерживаемой.
4. Прогон валидатора инвариантов (4.7).

Импорт **заменяет** документ целиком и не сливает. Слияние двух историй без идентификаторов устройств и векторов версий — отдельная задача, которая в офлайн-приложении для одного человека не окупается. Перед заменой автоматически снимается бэкап текущего состояния.

---

### 4.6. Версии схемы и миграции

`schemaVersion` — целое, растёт на единицу. Миграция — чистая функция `(doc) => doc`. При старте применяется цепочка от версии файла до текущей.

Правила:

- **Миграции никогда не удаляются из кода.** Файл двухлетней давности обязан открыться.
- Перед цепочкой снимается `backups/pre-migration-v{N}.json`. Он не входит в ротацию семи и не удаляется автоматически.
- **Файл с версией выше текущей не открывается.** Пользователь поставил старую сборку поверх новой; показывается сообщение, документ не трогается. Попытка прочитать будущую схему как текущую — самый надёжный способ потерять данные.
- Каждая миграция покрыта тестом на реальном снимке предыдущей версии.

История версий:

| Версия | Что изменилось |
|---|---|
| 1 | Первая модель: даты у повторяющихся платежей, подтверждение плановых. Не выпускалась |
| 2 | Переход на месячный учёт, `FixedItem` без дат |
| 3 | Виды потока `ROUTINE` / `ONE_OFF`, режим `SPREAD`, цели, месячная цель |
| 4 | Необязательное удержание налога на позиции дохода (`taxPercent`) |

---

### 4.7. Валидация при загрузке

Инварианты Части 1 проверяются на каждой загрузке. Не из перестраховки: файл мог быть импортирован, отредактирован руками или испорчен.

**Чинимые** проблемы правятся молча и пишутся в журнал: несортированный `amounts`, дубль `MonthOverride` (берётся последний), операция со ссылкой на исчезнувшую категорию (переносится в «Прочее»).

**Нечинимые** отменяют загрузку и ведут к восстановлению из бэкапа: сломанный JSON, дробные или отрицательные суммы, `schemaVersion` из будущего, `FixedItem` с пустым списком сумм.

Молчаливая потеря данных недопустима ни в одном из случаев. Если что-то поправлено — это видно в журнале; если не поправлено — приложение останавливается и говорит об этом.

---

### 4.8. Производительность и порог пересмотра

Индексы (`Map<MonthKey, Expense[]>`, оверрайды по ключу `месяц:позиция`) строятся один раз при загрузке и поддерживаются при мутациях.

Переходить на SQLite имеет смысл, если файл перевалит за 10 МБ или загрузка за 300 мс. При двух мегабайтах за пять лет это не наступит; до тех пор нативная база — преждевременная сложность.

---

### 4.9. Чего здесь нет

- **Облачной синхронизации.** Приложение офлайновое по решению из Части 1.
- **Шифрования файла.** Он лежит в приватной директории, добраться до неё можно только с root или с разблокированного устройства. Пин на приложении, которое открывают по десять раз в день, не окупается.
- **Журнала изменений.** Отмена работает в пределах сессии (полоса «Вернуть»), история правок не хранится.

---

### 4.10. Тестовые кейсы

**К1. Обрыв на записи.** `budget.tmp` записан наполовину, процесс убит. При следующем запуске `budget.json` цел, `budget.tmp` удаляется как мусор.

**К2. Файл из будущего.** `schemaVersion: 4` при поддержке 3 → отказ с сообщением, документ на диске не изменён.

**К3. Миграция 2→3.** У всех операций проставляется `flow` из `defaultFlow` категории; категории без него получают `ROUTINE`. Суммы месяцев до и после миграции совпадают.

**К4. Посторонний JSON.** Файл без `format` отвергается на второй проверке, до разбора содержимого.

**К5. Битая ссылка.** Операция ссылается на удалённую категорию → переносится в «Прочее», запись в журнале, загрузка продолжается.

**К6. Ротация.** Семь снимков, наступил восьмой день → удаляется самый старый; `pre-migration` остаётся.

---

### 4.11. Открытые вопросы

- Нужен ли CSV-экспорт операций для таблиц. Односторонний, импорта из CSV не будет.
- Восстановление из бэкапа: заменять документ целиком или давать выбрать, что именно взять оттуда. Второе заметно сложнее и нужно реже.
- Напоминание об экспорте. Удаление приложения уносит всё, и единственная защита — привычка выгружать файл. Вариант — ненавязчивая подсказка раз в месяц.

## Часть 5. Сборка и упаковка

### 5.1. Стек и почему именно он

| Слой | Решение | Почему |
|---|---|---|
| Сборка | Vite | Быстрый дев-сервер, простой выход в статику для Capacitor |
| UI | React + TypeScript в strict | Типы домена из Части 1 работают только при strict |
| Состояние | Zustand | Документ один, прокидывать его пропсами через все экраны незачем; Redux избыточен |
| Графики | Собственный SVG | Пять фиксированных типов графиков. Библиотека добавила бы сотни килобайт и свой подход к цветам, а нам нужно, чтобы подложка и сетка брались из CSS-токенов темы |
| Даты | Своё | Нужно шесть функций из 2.2, все на разборе строки. `date-fns` тянет то, чего мы сознательно избегаем — парсинг `Date` с таймзонами |
| Оболочка | Capacitor | Filesystem, Share, App (событие `pause`), StatusBar |
| Тесты | Vitest | Один рантайм со сборкой |

UI-китов нет. Компоненты свои, оформление на CSS-переменных из 3.9.

---

### 5.2. Структура проекта

```
src/
  domain/      типы, инварианты, валидатор          → Часть 1
  engine/      чистые расчёты                        → Часть 2
  storage/     файл, атомарная запись, миграции      → Часть 4
  store/       Zustand, мутации документа
  ui/
    screens/   Главная, Расходы, Цели, Дашборды, Календарь, Настройки
    components/
    theme.css  токены светлой и тёмной темы
  App.tsx
tests/
```

**Жёсткое правило: `engine/` не импортирует ничего из `ui/`, `storage/` и `store/`.** На вход документ и дата, на выход числа. Это не эстетика архитектуры, а условие того, что тестовые кейсы из 2.14 вообще можно написать.

---

### 5.3. Тесты

Обязательный минимум — кейсы из 2.14 и 4.10, каждый отдельным тестом с теми же числами.

Системные часы не мокаются нигде: `today` всегда приходит параметром. Если в тесте понадобился мок времени, значит нарушено правило из 2.1.

Проценты покрытия не назначаются. Покрыты должны быть сценарии в `engine/` и `storage/migrations`, а не строчки.

---

### 5.4. Сборка APK

```
npm run build          # → dist/
npx cap sync android   # переносит dist и плагины в проект android/
cd android
./gradlew assembleDebug     # или assembleRelease
```

Среда: JDK 21 (Capacitor 7 требует именно 21), Android SDK Platform 35 с Build-Tools, переменная `ANDROID_HOME`. Node 20+.

Debug-сборка ставится на телефон напрямую. Release требует подписи.

---

### 5.5. Подпись

Keystore создаётся один раз:

```
keytool -genkey -v -keystore budget.keystore -alias budget \
        -keyalg RSA -keysize 2048 -validity 10000
```

Keystore и пароль в репозиторий не попадают никогда: `keystore.properties` в `.gitignore`.

**Потерянный keystore означает, что обновить установленное приложение нельзя.** Android откажется ставить APK с другой подписью поверх существующего, останется только удалить — а удаление вычищает приватную директорию вместе со всей историей бюджета (4.1). Поэтому keystore хранится там же и так же надёжно, как экспорты бюджета. Это единственный файл проекта, потеря которого необратима.

---

### 5.6. Версии

- `versionCode` — целое, растёт на единицу с каждой сборкой, которая ставится на телефон. Android не даст установить APK с кодом ниже установленного.
- `versionName` — человеческая строка, попадает в конверт файла как `appVersion` (4.2).

**Любое изменение `schemaVersion` обязано поднимать `versionName`.** Иначе по экспортному файлу нельзя будет понять, какая сборка его написала, и разбор проблемы с миграцией превратится в гадание.

---

### 5.7. Обновление установленного приложения

Собрать, подписать тем же keystore, поднять `versionCode`, поставить поверх. Данные переживают обновление: файл лежит в приватной директории, обновление её не трогает.

Перед сборкой, которая поднимает `schemaVersion`, миграция прогоняется **на реальном экспорте со своего телефона**, а не на синтетическом документе. Синтетика не содержит того, что накопилось за полгода ручного ввода, и именно на этом миграции и ломаются.

---

### 5.8. Настройки Capacitor

- `webDir: 'dist'`, свои `appId` и `appName`.
- StatusBar следует теме приложения: переключатель в шторке меняет и цвет статус-бара, иначе вверху экрана останется светлая полоса при тёмной теме.
- Отключить overscroll-отскок и зум жестами: приложение не веб-страница.
- `allowMixedContent: false`. Сеть не используется вообще.

---

### 5.9. Чего не делаем

- **Не публикуем в Play.** Приложение личное, установка боковая.
- **Не подключаем аналитику и краш-репортинг.** Они требуют сети, а приложение офлайновое по решению из Части 1.
- **Не тянем иконочные шрифты.** Иконки инлайновым SVG, как в прототипе.
- **Шрифт Golos Text кладём в бандл**, а не грузим с Google Fonts. В прототипе он подключён ссылкой, и это правильно для веба, но в офлайн-приложении зависимость от сети ради шрифта недопустима: без интернета интерфейс поедет на системном фолбэке.

---

### 5.10. Порядок реализации

1. `domain/` — типы и валидатор инвариантов.
2. `engine/` — расчёты и тесты из 2.14. Интерфейса ещё нет.
3. `storage/` — запись, бэкапы, миграции, тесты из 4.10.
4. `ui/` — экраны по Части 3.
5. Capacitor, подпись, APK на телефоне.

Первые три шага проверяются тестами и не требуют телефона вообще. Если начать с интерфейса, ошибки в арифметике всплывут поздно и искать их придётся через экран, где видно следствие, а не причину.

### 5.11. Открытые вопросы

- Собирать APK локально или настроить GitHub Actions. Локально проще, но keystore тогда живёт только на одной машине.
- Иконка приложения и splash-экран.
- Нужен ли режим разработки с подставным документом на полгода истории, чтобы видеть дашборды не на пустом месте. Скорее да — иначе первые недели проверить статистику будет не на чем.
