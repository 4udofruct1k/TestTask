# Промпты для Claude Code

В репозитории должны лежать два файла: `BUDGET_SPEC.md` и `design/mockup.html` (прототип экранов, эталон вёрстки для шага 4).

---

## Постоянный контекст

Этот блок вставляется в начало **каждой** сессии, независимо от шага.

```
Мы строим офлайновое приложение учёта бюджета: React + TypeScript + Vite,
упаковка в APK через Capacitor. Ни сервера, ни сети. Одна валюта, рубли.

Спецификация — BUDGET_SPEC.md в корне. Это источник истины, а не пожелание.
Прочитай её целиком прежде чем писать первую строку кода.

Жёсткие правила, нарушение любого — повод переделать:

1. Деньги — целые копейки (тип Money = number). Ни одного float в домене
   и в хранилище. Округление только на слое отображения.
2. Даты — строки "YYYY-MM-DD" и "YYYY-MM", разбираются посимвольно.
   В src/domain и src/engine конструктор Date запрещён полностью:
   new Date("2026-03-16") парсится как UTC, new Date(2026,2,16) как
   локальное время, и смешение этих путей даёт сдвиг на сутки.
3. Сегодняшняя дата всегда приходит параметром. Ни одна функция расчёта
   не читает системные часы. Если в тесте понадобился мок времени —
   правило нарушено, чини код, а не тест.
4. src/engine не импортирует ничего из src/ui, src/storage, src/store.
   Вход — документ и дата, выход — числа.
5. Не выдумывай полей, правил и значений по умолчанию, которых нет
   в спецификации. Если чего-то не хватает или спека противоречит сама
   себе — остановись и спроси. Не достраивай по смыслу.
6. Комментарии по-русски, код и идентификаторы по-английски.
```

## Шаг 1 — домен

```
Читай BUDGET_SPEC.md, Часть 1 целиком и раздел 2.2.

Сделай:

src/domain/types.ts
  Все типы Части 1: Money, MonthKey, DateStr, Category, Expense,
  FixedItem (union MONTHLY | SPREAD), AmountPeriod, SpreadPeriod,
  MonthOverride, MonthlyTarget, SavingsGoal, Contribution,
  BudgetDocument, Settings.

src/domain/money.ts
  Разбор ввода в копейки, форматирование в рубли (целые в списках,
  с копейками в правке), защита от нецелых значений.

src/domain/dates.ts
  Примитивы из 2.2: monthKeyOf, dayOfMonth, daysInMonth, addMonths,
  monthsBetween, compareMonth, monthRange. Только работа со строками.

src/domain/validate.ts
  Проверка инвариантов Части 1. Возвращает { fixed: Fix[], fatal: Fatal[] }
  по классификации из 4.7: чинимое правится и попадает в fixed,
  нечинимое попадает в fatal и останавливает загрузку.

tests/
  dates: високосный год (2024, 2100, 2000), addMonths через границу года,
  daysInMonth для всех двенадцати месяцев.
  validate: каждый нечинимый класс из 4.7 ловится, каждый чинимый
  правится и регистрируется.

Ничего, кроме перечисленного. UI, хранилища и расчётов на этом шаге нет.
Когда закончишь — покажи типы и список тестов, не пересказывай спеку.
```

## Шаг 2 — расчётный движок

```
Читай Часть 2 целиком.

Сделай src/engine: amountAt, resolveFixed, expensesOfMonth,
monthSummary, cumulativeByDay, compareToPrevious, темп и прогноз,
usualDaily и potentialExtra, targetStatus, goalProgress,
annualCalendar, oneOffAnalysis, агрегацию по периодам.

Приёмка — тестовые кейсы 2.14, К1 по К11, каждый отдельным тестом
с ровно теми числами, что в спеке. Тест, который не сходится,
означает ошибку в коде, а не повод поправить ожидаемое значение.
Если считаешь, что в спеке ошибка в числах — скажи, не правь молча.

Отдельно проверь три места, где легко ошибиться:
— medianа в usualDaily против среднего в oneOffAnalysis (2.8 и 2.12),
  это разные решения по разным причинам, не унифицируй их;
— остаток от деления в SPREAD уходит в последний месяц цикла;
— ставка накопления за период это отношение сумм, а не среднее
  из месячных ставок.
```

## Шаг 3 — хранилище

```
Читай Часть 4 целиком.

Сделай src/storage: конверт файла, атомарная запись через tmp
с проверкой и переименованием, дебаунс и запись по событию pause,
суточная ротация семи бэкапов, цепочка миграций, экспорт и импорт.

Приёмка — кейсы 4.10, К1 по К6. Кейс К1 (обрыв на записи)
воспроизводится подменой файлового слоя, а не реальным убийством
процесса: файловый доступ должен быть за интерфейсом,
чтобы его можно было подменить в тесте.

Миграции 1→2 и 2→3 пиши сразу, даже если первых версий в природе
не было: цепочка должна существовать с самого начала, иначе
её никто не заведёт потом.
```

## Шаг 4 — интерфейс

```
Читай Часть 3 целиком и открой design/mockup.html — это работающий
прототип, эталон вёрстки, цветов и поведения. Токены бери из 3.9.

Порядок: сначала Главная, потом Расходы с двумя вкладками,
потом Дашборды, потом Цели, Календарь и Настройки.

Важное:
— подложка и сетка графиков берутся из CSS-токенов, иначе при
  тёмной теме графики останутся белыми;
— прогноз и факт не смешиваются в одном числе никогда;
— правка постоянной позиции предлагает выбор между смыслами
  («изменить с апреля» / «исправить ошибку»), а не между режимами;
— удаление постоянной позиции действует с текущего месяца вперёд
  и не переписывает прошлое;
— числительные склоняются везде.

Графики пиши своим SVG, библиотеку не подключай.
```

## Что говорить, когда что-то идёт не так

- **Claude Code достроил правило, которого нет в спеке** — «это не из спеки, покажи откуда взял или убери».
- **Тест не сходится и он правит ожидание** — «ожидания из 2.14 менять нельзя, чини расчёт».
- **Появился `new Date(...)` в engine** — «правило 2 постоянного контекста».
- **Начал делать UI раньше времени** — «шаг N, интерфейса на нём нет».
